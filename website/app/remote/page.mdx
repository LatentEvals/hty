# Remote Sessions

Drive and observe sessions running on other machines — no special protocol, just an SSH tunnel.

## Why

Your agent runs locally but needs to interact with a program on a remote server: a database REPL, a deployment wizard, a debugging session. With `hty` and an SSH tunnel, you can `watch`, `attach`, `snapshot`, and `send` to remote sessions as if they were local.

## Setup

### On the remote machine

Start a session as usual:

```sh
hty run --name deploy -- ./deploy.sh production
```

### Find the remote socket path

Run `hty info` on the remote machine to see the socket path:

```sh
$ hty info
socket:  /run/user/1000/hty/sock
logs:    /home/user/.local/state/hty/logs
server:  running
```

The socket path depends on the environment — on Linux with systemd it's typically `/run/user/{uid}/hty/sock`, otherwise it's `~/.local/state/hty/sock`. `hty info` resolves it for you.

### On your laptop

Create an SSH tunnel that forwards the remote hty socket to a local path. Use the socket path from `hty info` on the remote:

```sh
# Linux remote with systemd
ssh -L ~/.local/state/hty/remote.sock:/run/user/1000/hty/sock user@remote

# macOS remote or Linux without XDG_RUNTIME_DIR
ssh -L ~/.local/state/hty/remote.sock:/home/user/.local/state/hty/sock user@remote
```

Then point `hty` at the forwarded socket:

```sh
# watch what the deploy script is doing
HTY_SOCKET=~/.local/state/hty/remote.sock hty watch deploy

# read the screen programmatically
HTY_SOCKET=~/.local/state/hty/remote.sock hty snapshot deploy

# send input
HTY_SOCKET=~/.local/state/hty/remote.sock hty send deploy --text "y\n"

# attach interactively
HTY_SOCKET=~/.local/state/hty/remote.sock hty attach deploy
```

Every command works the same — `watch`, `attach`, `snapshot`, `send`, `wait`, `list`, `logs`, `replay`. No protocol changes.

## How it works

When `$HTY_SOCKET` is set, `hty` connects to that socket instead of the default local one. It never auto-spawns a local server in this mode — if the tunnel is broken, you get a fast failure instead of silently connecting to a fresh local server.

## Practical patterns

### Export the variable for a session

```sh
export HTY_SOCKET=~/.local/state/hty/remote.sock

# now all commands target the remote server
hty list
hty snapshot deploy
hty send deploy --text "y\n"
```

### Multiple remotes

Use different socket paths for each machine:

```sh
ssh -L ~/.local/state/hty/staging.sock:/run/user/1000/hty/sock user@staging
ssh -L ~/.local/state/hty/prod.sock:/run/user/1000/hty/sock user@prod

HTY_SOCKET=~/.local/state/hty/staging.sock hty list
HTY_SOCKET=~/.local/state/hty/prod.sock hty list
```

### Agent-driven remote automation

Your agent can drive an interactive program on a remote server the same way it drives local ones:

```sh
export HTY_SOCKET=~/.local/state/hty/remote.sock

hty run --name db -- psql -U postgres production

hty wait db --text "production=#" --timeout 5000
hty send db --text "SELECT count(*) FROM orders WHERE status = 'pending';\n"
hty wait db --idle 500 --timeout 5000
hty snapshot db
```
