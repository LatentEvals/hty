# How It Works

`hty` is a single binary that runs a persistent PTY server and exposes it through a flat CLI. No runtime dependencies, no daemon to configure, no containers.

## The model

```
Agent/script          hty CLI           hty server          Program
     │                   │                  │                   │
     │── hty run ──────> │── spawn ───────> │── forkpty ──────> │
     │                   │                  │                   │
     │── hty send ─────> │── input ───────> │── write(pty) ───> │
     │                   │                  │                   │
     │── hty snapshot ─> │── read ────────> │                   │
     │<── rendered screen │<── VT engine ── │<── read(pty) ──── │
     │                   │                  │                   │
     │── hty wait ─────> │── poll ────────> │                   │
     │<── (returns) ──── │<── condition met │                   │
```

The server owns the PTY and the VT engine. Clients talk to it over a Unix socket. The CLI is stateless — every invocation connects, does one thing, and exits.

## Why the output is readable

When you run `hty snapshot`, you don't get raw ANSI escape sequences. You get the rendered screen — the same thing a human sees when they look at their terminal.

This is because `hty` runs every byte of program output through [Ghostty](https://ghostty.org)'s VT engine, a production-grade virtual terminal that handles cursor movement, color palettes, alt-screen switching, and every SGR edge case that real programs use. The snapshot reads from the VT engine's in-memory screen buffer, not from the raw byte stream.

This matters because agents parse text, not escape codes. A raw `btop` output stream is unintelligible. A rendered `btop` screen is a table of processes with CPU percentages.

## Why Zig and Ghostty

The project started as a Rust prototype with `tokio`, `portable-pty`, and the `vt100` crate. The architecture worked, but the VT parser couldn't faithfully reproduce programs like `btop` — rapid cursor movement, dynamic palettes, SGR edge cases, and alt-screen transitions broke it.

The lesson: **use a production VT engine, don't build one.** Ghostty's terminal core is the state machine behind a real terminal emulator used by thousands of developers daily. It's exposed as a Zig module, so `hty` imports it directly — no FFI boundary, no serialization overhead.

Zig also makes the server simpler. `forkpty` + a reader thread + a mutex is the entire concurrency model. No async runtime, no colored functions, no hidden state machines.

## Session persistence

Every session is recorded to an append-only JSONL file at `$XDG_STATE_HOME/hty/logs/`. Each event is one of:

- **spawn** — session started, records the command and environment
- **output** — raw PTY bytes from the program
- **input** — bytes sent to the program
- **title** — terminal title change (set by the program)
- **bell** — terminal bell
- **exited** / **failed** / **killed** — session ended

Named sessions get a symlink, so `hty logs my-session` resolves to the right file.

This means:
- `hty logs` works after the session exits, after the server restarts, indefinitely
- `hty replay` feeds the logged output through a fresh VT engine in memory — perfect fidelity, no side effects
- Crash forensics are always available

## Server lifecycle

- **Auto-start**: the first `hty` command spawns the server via exec if it isn't running (like tmux)
- **Auto-shutdown**: the server exits after 10 seconds of idle
- **Restart recovery**: `hty list` scans the log directory on disk, so historical sessions appear even after a server restart
- **Permissions**: uses XDG runtime/state paths with 0700 permissions. The socket is only accessible to the owning user
- **No config files**: there's nothing to configure. It just works.

## What `hty` is not

- **Not a terminal emulator.** It doesn't draw to your screen. It hosts sessions that other tools (agents, scripts, humans via `watch`/`attach`) interact with.
- **Not a tmux replacement.** tmux is for humans managing terminal windows. `hty` is for programmatic automation of interactive programs.
- **Not an expect clone.** `expect` matches on the output byte stream. `hty` matches on the rendered screen — a fundamental difference for programs that use cursor movement, clearing, and redrawing.
